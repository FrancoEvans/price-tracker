# Alembic migration workflow

Migrations run on **psycopg2 (sync)** even though the app runs on **asyncpg
(async)** at runtime. Alembic and the app deliberately use different drivers
against the same database — this is intentional, do not "fix" it.

## When to run this

After any change to a model under `app/products/models/` or `app/users/models/`
(new table, new column, type change, constraint change). Editing the ORM class
does nothing to the database on its own: the change only exists once a migration
is generated, reviewed, and applied.

## Steps

1. **Confirm the changed/new model is imported in `alembic/env.py`.**
   `--autogenerate` only detects models that are imported at the moment env.py
   runs. If you added a new model file (for example a bot-related model) and did
   not import it there, autogenerate produces an empty or partial migration and
   silently skips your table — the single most common failure in this project.

   ```bash
   grep -n "import" alembic/env.py
   ```

   Every model module must appear. If the new one is missing, add the import
   before generating anything.

2. **Generate the migration** with a short imperative message:

   ```bash
   alembic revision --autogenerate -m "add category to products"
   ```

3. **Read the generated script in `alembic/versions/` before applying it.**
   Autogenerate is not trustworthy for:
   - **Renames** — it emits `drop_column` + `add_column`, which destroys the data
     in that column. Replace both with a single
     `op.alter_column("table", "old_name", new_column_name="new_name")`.
   - **Type changes** — sometimes detected, sometimes not. Verify the
     `alter_column` type is the one you intended.
   - **Server defaults and check constraints** — frequently missed; add them by hand.

   Confirm `upgrade()` does exactly what you meant and `downgrade()` is its inverse.

4. **Apply it:**

   ```bash
   alembic upgrade head
   ```

5. **Verify** the database is at the latest revision:

   ```bash
   alembic current   # must match the id shown by: alembic heads
   ```

   To inspect the actual table, connect by database name — NOT via `$DATABASE_URL`,
   which contains `+asyncpg` and psql cannot parse it:

   ```bash
   psql -d price_tracker -c "\d+ products"
   ```

## Do NOT

- Do not run migrations against `price_tracker_test`. The test suite builds its
  schema with `create_all` in `conftest.py`, not with alembic, so migrating it
  achieves nothing.
- Do not edit a migration that has already been applied and committed. Generate a
  new one instead.
- Do not hand-write a migration from scratch when a model change can be
  autogenerated and reviewed — writing it by hand drifts from the models.

## Common failure

`--autogenerate` produced an empty migration (`pass` in both `upgrade()` and
`downgrade()`) right after you added a model → the model is not imported in
`alembic/env.py`. Go back to step 1.
